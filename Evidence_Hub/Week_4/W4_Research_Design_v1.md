## 3. Consent / Data Plan（成品，直接执行）

**我们收集什么**
- 只收集：校区、年级、使用场景、顾虑、押金态度、原型操作表现。
- 不收集：姓名、学号、手机号、身份证、微信昵称、宿舍号、照片。

**怎么存**
- 访谈与测试记录一律用匿名编号 U01-U05 / T01-T05，文件存在 `Evidence_Hub/Week_5/`。
- 问卷通过问卷星/腾讯问卷收集，不采集 IP 以外的可识别信息；导出后只保留汇总结果。
- 录音（如果用）在转写成文字后立即删除，不放进 Evidence Hub。

**怎么用**
- 只用于 ENT303TC 课程项目，不对外发布、不商用。
- 引用原话时去掉所有可识别信息，并在旁边标注编号。

**同意怎么拿**
- 访谈：念 `W05_访谈执行包_v1.md` 第 1 节的同意话术，对方口头同意后开始，在记录表里写「口头同意 + 日期」。
- 问卷：开头写明用途、匿名性和「提交即表示同意参与」。
- 原型测试：测试前说明「这是原型，不是真实交易，不会产生任何费用」。

## 4. 反偏差设计（导师最容易挑这里）

| 会犯的错 | 我们怎么避免 |
|---|---|
| 诱导性问题：「你觉得这个平台有用吗？」 | 改问经历：「过去一学期你有没有临时需要过某件东西但不想买？」 |
| 只问朋友（全是熟人样本） | 至少 1 名非熟人、1 名太仓学生；记录表里标「熟人 / 非熟人」 |
| 边讲边教，用户没有自己的判断 | 先问当前行为，再展示原型；测试时不给提示，观察用户自己能否找到 |
| 只收集支持自己的证据 | Weekly Log 必须写「反面 / 负面证据」，问卷数据不许删不符合预期的答卷 |
| 把假设说成事实 | 一律写 "we hypothesise" / "early validation suggests" |

## 5. Pilot（试跑，15 分钟）

在正式访谈前，先找 1 名组员当"假受访者"跑一遍 8 个问题：

- 哪一题对方听不懂？→ 改措辞，不要改问题意图。
- 哪一题回答只有"是/不是"？→ 加一个追问。
- 全程几分钟？→ 超过 20 分钟就砍问题。

试跑记录写在 `Evidence_Hub/Week_5/W05_访谈执行包_v1.md` 末尾的备注里，**不要把组员的回答当成用户证据**。

## 6.1 Week 4 原型 Pilot 任务（新增，2026-09-28）

这周先不追求完整上线，而是验证“这个产品能不能被真实学生理解并完成关键动作”。每位测试者只做 5 个任务，Rita 或汪r 操作电脑，黄jj 记录观察。

| 任务 | 成功标准 | 记录什么 |
|---|---|---|
| T1 找物品 | 60 秒内找到一件自己可能会用的物品 | 搜索词、筛选方式、是否切换校区 |
| T2 看规则 | 能说出押金、可用时间、归还规则 | 哪个字段没注意到 |
| T3 发预约 | 能填写交付点、借出时间、归还时间并提交 | 是否理解“预约待确认” |
| T4 发布物品 | 能提交一个开放物品表单 | 是否理解“先审核再展示” |
| T5 管理端理解 | 看管理端 30 秒后能说出后台处理什么 | 是否能理解审核/借还/举报三类队列 |

测试前运行：

```bash
cd xjtlu-market-app
npm run reset
npm run build
npm run dev
```

测试后把观察写进 `Evidence_Hub/Week_5/` 的用户记录模板，不要写真名；如果只是组员试跑，标注为 pilot，不算正式用户证据。

## 6.2 Week 4 代码状态（给导师/组员解释用）

当前原型已经从展示页变成可测试 MVP：

- 学生发布物品后进入“审核中”，管理员通过后才在学生端出现。
- 预约会写入 `data/bookings.json`，不是只弹 toast。
- 举报会写入 `data/reports.json`，管理端能处理。
- 管理端展示真实队列：物品审核、借还预约、举报争议、最近物品状态。
- `npm run reset` 会恢复商品、预约、举报三类演示数据。

仍然不能声称真实运营：

- 没有真实邮箱验证码/SSO。
- 没有云数据库和线上部署。
- 没有真实支付、押金托管和客服流程。
- 没有真实聊天和消息推送。
