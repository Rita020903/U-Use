# 校园版闲鱼 PRD 初稿

## 1. 文档信息

- 产品暂名：校园闲置交易平台
- 文档版本：V0.2
- 文档状态：概念验证 / 原型设计中
- 目标用户：在校大学生
- 首次上线范围：西交利物浦大学双校区试点
- 核心定位：基于校园身份认证的可信二手物品交易平台
- 首个试点学校：西交利物浦大学（XJTLU）
- 首选身份认证方式：西浦学生邮箱验证
- 首选产品形态：微信内可访问的移动端 Web App / H5 链接，后续可迁移为微信小程序或独立 App

## 2. 产品概述

### 2.1 产品背景

学生在毕业、搬宿舍、换专业或日常生活中会产生大量闲置物品，例如教材、考研资料、数码产品、宿舍用品、自行车、乐器和运动装备。

现有综合二手平台通常存在以下问题：

1. 买卖双方不在同一校园，沟通、运输和交付成本较高。
2. 用户身份难以确认，诈骗、虚假商品和交易纠纷降低信任。
3. 学生真正关心的是“附近有没有、能不能当面看、什么时候可以取”。
4. 校园内有大量临时性需求，但信息分散在微信群、QQ群和朋友圈中，难以搜索和沉淀。

### 2.2 产品愿景

让校园里的每件闲置物品，都能更快、更安全地找到下一位需要它的同学。

### 2.3 核心价值

- 对买家：更容易找到同校、距离近、可当面验货的低价商品。
- 对卖家：更快卖掉闲置，减少打包、发货和沟通成本。
- 对学校：减少闲置浪费，促进校园循环利用。
- 对平台：通过校园身份和交易行为建立可信的校园社区。

### 2.4 西浦试点设定

首个版本面向西交利物浦大学学生，默认使用西浦学生邮箱完成校园身份验证。平台后台配置允许的学校邮箱域名，前端只展示“西浦学生 / 已认证”标识，不展示完整邮箱、学号或身份证信息。

邮箱验证证明的是用户能够控制该学校邮箱，不等同于公开学生学号或完成法律意义上的实名核验。因此，平台对外应使用“校园邮箱已验证”等准确表述。

### 2.5 产品形态判断

首期不建议一次性开发完整原生 App。更适合的路径是：

1. 先做微信内可打开的移动端 Web App / H5 链接，用于原型展示、同学内测和快速迭代。
2. 用户端按手机使用场景设计，重点保证浏览、发布、聊天、预约和个人中心完整可用。
3. 管理端做成桌面优先的 Web 看板，用于认证、商品、举报、交易和数据运营。
4. 当真实用户和交易数据验证后，再决定是否开发微信小程序或原生 App。

选择微信链接的原因是传播成本低，适合通过班级群、社团群、朋友圈和活动海报拉新；同时用户不需要下载安装，适合早期验证。需要注意的是，微信 H5 仍然需要稳定的后端、数据库、图片存储、域名和 HTTPS，不能只靠本地电脑长期运行。

## 3. 产品目标与非目标

### 3.1 首期目标

首版只验证三个问题：

1. 学生是否愿意完成校园身份认证。
2. 学生是否愿意在平台发布和浏览闲置物品。
3. 买卖双方能否通过平台完成一次真实的线下交易。
4. 微信链接入口是否足够支撑学生端传播和日常使用。
5. 双校区场景下，用户是否能理解“本校区优先、跨校区可约”的交易方式。

### 3.2 首期成功标准

- 新用户注册后能够顺利完成校园认证。
- 用户可以在 1 分钟内发布一件闲置物品。
- 买家可以按校区、分类、价格、距离和交易方式快速找到商品。
- 买卖双方可以在平台内完成沟通、预约和交易状态确认。
- 平台能够处理举报、违规商品和恶意用户。
- 用户可以通过微信链接打开平台，并完成登录、浏览、发布或咨询流程。

### 3.3 首期不做

- 全国范围的跨城交易。
- 平台自建物流。
- 复杂的商城、直播和内容电商。
- 面向未认证用户的公开交易。
- 未完成合规评估前的平台资金托管和担保支付。
- 以“公开实名”作为信任方式。平台可以验证真实身份，但不应公开用户的完整姓名、学号或身份证信息。
- 首期不开发完整原生 App。除非后续验证需要，否则先用微信 H5 / 小程序路线承载。
- 首期不把跨校区商品伪装成“附近”。跨校区是独立交易方式，需要明确交付点、时间和风险提示。

## 4. 用户角色

### 4.1 买家

希望低价购买同校闲置物品，并优先选择可以当面验货和自提的商品。

### 4.2 卖家

希望快速发布商品、收到咨询、约定交付并及时完成出售。

### 4.3 平台管理员

负责用户认证、内容审核、举报处理、违规处罚、数据统计和校园运营。

### 4.4 校园运营人员（可选）

负责校园推广、毕业季活动、失物与闲置专区运营。首版可以由平台管理员兼任。

### 4.5 产品端划分

#### 学生用户端

学生用户端是首期主产品，面向手机竖屏使用。核心任务是让用户通过微信链接快速进入、完成认证、发现商品、发布商品、沟通预约和完成交易。原型和视觉设计应优先围绕这一端展开。

#### 运营管理端

运营管理端不是给普通学生使用的“客户端”，而是给项目团队、管理员和校园运营人员使用的后台看板。它应以桌面 Web 为主，优先解决审核、举报、用户封禁、数据统计和运营配置，不需要做成手机 App。

## 5. 核心产品原则

1. **校园优先**：默认只展示用户所在学校的商品。
2. **身份可验证，信息不公开**：展示“已认证学生”标识，不展示完整学号和敏感身份信息。
3. **线下交付优先**：鼓励在校园公共区域当面验货和交付。
4. **交易过程可追踪**：从咨询、预约到完成，都有明确状态。
5. **安全机制前置**：举报、拉黑、风险提示和违规处理必须在首版具备。
6. **先跑通交易，再扩展社区**：首版重点是商品和交易闭环，不急于做复杂内容社区。
7. **本校区优先，跨校区可选**：双校区不是简单扩大范围，而是让用户清楚看到商品在哪个校区、如何交付、是否值得跨校区交易。
8. **微信入口友好**：首期产品需要适合从微信群、朋友圈和二维码进入，减少下载和注册阻力。

## 7. MVP 功能范围

### 7.1 用户注册与校园认证

#### 功能说明

用户注册后必须完成校园身份认证，认证通过后才能发布商品、发送交易消息或发起预约。

#### 推荐认证方式

优先级从高到低：

1. 学校官方邮箱验证。
2. 学校统一身份认证或校园门户登录。
3. 学生证 / 学籍证明上传，由人工或第三方服务审核。
4. 手机号验证只能作为账号安全验证，不能单独作为学生身份认证。

#### 展示规则

- 个人主页展示：已认证学生、所在学校、入学年份或年级区间。
- 不展示：完整学号、身份证号、学生证照片、手机号。
- 数据存储：尽量只保存认证结果、学校、认证时间和必要的过期时间，不保存不必要的原始证件。
- 毕业后：可以保留历史交易记录，但默认不能继续发布新的校园商品，具体规则可按学校运营策略决定。

#### 验收标准

- 未认证用户不能发布商品、发送私信或预约交易。
- 认证失败时说明失败原因，并支持重新提交。
- 用户可以查看认证状态和隐私说明。
- 管理员可以查看认证记录并处理异常账号。

### 7.2 首页与商品浏览

#### 商品卡片展示

- 商品图片
- 商品标题
- 价格
- 成色
- 发布者认证标识
- 发布时间
- 取货范围或校区
- 商品状态：在售、已预订、已售出

#### 筛选与排序

- 分类
- 价格区间
- 成色
- 校区
- 交易方式：当面交易 / 校内配送 / 其他
- 排序：综合、最新、价格从低到高、价格从高到低、距离优先
- 本校区优先
- 跨校区可交易
- 仅看可预约

#### 首版分类建议

- 教材与资料
- 数码产品
- 宿舍用品
- 服饰鞋包
- 自行车与交通
- 乐器与运动
- 化妆与生活用品
- 其他

### 7.2.1 校园地图与附近发现

#### 功能定位

地图不是用来精确追踪学生位置，而是帮助买家理解“这个商品大概在哪个校区、离我远不远、适合在哪里交付”。首版应避免展示卖家宿舍或实时位置，只展示大致区域、公共交付点和商品聚合点。

#### 地图范围

- 苏州工业园区校区：展示主要教学楼、图书馆、宿舍区附近、食堂、校门、快递点等公共区域。
- 太仓校区：展示主要教学区、宿舍区、食堂、图书馆、校门、校车点等公共区域。
- 两个校区之间不显示“直线附近”，而是显示交通与交付建议。

#### 开启定位后

- 用户可选择授权定位。
- 定位只用于计算附近商品和推荐交付点。
- 前端展示“约 x 米 / 本校区 / 跨校区”，不展示精确坐标。
- 用户可随时关闭定位或改为手动选择校区。

#### 附近推荐规则

优先级建议：

1. 当前校区内、距离近、在售、近期活跃商品。
2. 当前校区内、价格或成色更优商品。
3. 当前校区内可立即预约商品。
4. 跨校区但卖家标记“可约校车点 / 可去对方校区”的商品。
5. 跨校区普通商品，默认不进入附近推荐，只在跨校区筛选中展示。

#### 交付点设计

平台应预设公共交付点，例如图书馆门口、食堂入口、快递点、校车点、校门附近等。交易预约时优先让双方从公共交付点中选择，减少暴露宿舍具体位置的风险。

#### 验收标准

- 未授权定位时，用户仍可通过手动选择校区浏览商品。
- 授权定位后，用户可以切换距离优先、价格排序和本校区优先。
- 地图上不展示任何用户的实时位置和精确宿舍位置。
- 跨校区商品有明确标识，不被误认为“附近商品”。

### 7.3 搜索

#### 功能说明

用户可以通过关键词搜索当前校园内的商品。

#### 首版要求

- 支持标题和描述关键词搜索。
- 支持搜索历史。
- 支持热门搜索词。
- 搜索结果默认只展示当前学校商品。
- 无结果时提供“发布求购”入口，求购功能可以作为 P1。

### 7.4 发布商品

#### 发布字段

- 商品图片：最多 9 张，至少 1 张。
- 商品标题：建议 5 至 30 字。
- 分类。
- 售价：支持免费、议价和固定价格。
- 成色：全新、几乎全新、轻微使用、明显使用痕迹、功能问题。
- 商品描述。
- 商品问题说明：维修史、瑕疵、缺少配件等。
- 交易方式：公共区域当面交易、宿舍楼下交付、校内配送。
- 可交易时间。
- 取货校区或大致区域。
- 是否允许议价。
- 是否支持跨校区交易。
- 跨校区交付方式：卖家可去对方校区 / 买家自取 / 校车点交付 / 仅本校区可取。

#### 发布约束

- 标题不能使用“官方”“内部渠道”等误导性词语。
- 商品必须真实存在，禁止盗图和虚假描述。
- 不允许发布违禁、危险、侵权、处方类或学校规定禁止交易的物品。
- 发布前展示安全提示：不要提前支付，不要点击陌生链接，不要泄露验证码。

#### 商品状态

- 草稿
- 审核中
- 在售
- 已预订
- 已售出
- 已下架
- 审核拒绝

### 7.4.1 求购 / 想要

求购功能建议作为 P1，但设计稿中可以提前体现入口。它适合解决“学生想买但平台暂时没有供给”的问题，也能帮助平台判断真实需求。

#### 求购字段

- 想买的商品名称
- 预算区间
- 分类
- 期望校区
- 是否接受跨校区
- 备注说明
- 有效期

#### 触发入口

- 搜索无结果页
- 分类页顶部
- 首页运营区
- 商品详情页相关推荐区域

#### 首期策略

如果开发资源有限，V0.1 可以只做“发布求购信息”和“卖家可联系求购者”，暂不做复杂匹配算法。

### 7.5 商品详情

#### 页面内容

- 图片浏览
- 标题、价格、成色和描述
- 瑕疵及问题说明
- 发布者的认证状态和历史交易评价
- 取货校区 / 大致位置
- 交易方式和可交易时间
- 举报入口
- 分享入口
- 联系卖家按钮
- 预约交易按钮

#### 安全提示

根据商品价格、分类和聊天内容，展示适度风险提示，例如：

- 请当面验货后再付款。
- 不要私下点击陌生支付链接。
- 不要将验证码、密码或身份证照片发送给他人。
- 建议选择校内公共区域交付。

### 7.6 站内沟通

#### 首版功能

- 买家与卖家一对一聊天。
- 发送文字和图片。
- 商品卡片自动附带在会话中。
- 支持快捷语：还在吗、可以优惠吗、在哪里交付、什么时候方便。
- 支持举报、拉黑和删除会话。

#### 风控规则

- 对明显的诈骗话术、陌生链接、收款码和高风险联系方式进行提示或拦截。
- 不默认公开手机号、学号和身份证信息。
- 对短时间大量发送相同内容的账号限流。
- 聊天记录保留必要时长，用于处理举报和交易纠纷，并在隐私政策中明确说明。

### 7.7 预约与交易状态

首版不强制接入资金托管，先做“交易意向与状态记录”。

#### 交易流程

浏览商品 → 联系卖家 → 发起预约 → 卖家确认 → 当面验货 / 交付 → 双方确认完成 → 评价或举报

#### 交易状态

- 待确认
- 已预约
- 交易中
- 已完成
- 已取消
- 争议处理中

#### 预约信息

- 交易商品
- 交易双方
- 交付方式
- 约定时间
- 约定地点
- 交付校区
- 是否跨校区
- 备注

#### 重要规则

- 交易地点只允许填写大致公共区域，不要求公开具体宿舍房间号。
- 跨校区预约必须明确由谁移动、在哪里交付、是否需要校车或额外时间。
- 卖家确认预约后，商品自动显示“已预订”，可设置预约有效期。
- 任一方可以取消预约，需要填写简单原因。
- 交易完成后，双方可以互评。
- 评价不能修改他人身份信息或发布隐私内容。

### 7.7.1 双校区交易规则

西浦存在苏州工业园区校区和太仓校区，首期不能把两个校区简单合并成一个“附近市场”。推荐设计为三种交易范围：

| 范围 | 含义 | 默认展示策略 |
|---|---|---|
| 本校区可取 | 商品只在当前校区交付 | 首页和附近推荐优先展示 |
| 跨校区可约 | 卖家或买家愿意跨校区协调 | 作为独立标签和筛选项展示 |
| 仅指定校区 | 商品只在卖家指定校区交易 | 不进入其他校区的附近推荐 |

#### 跨校区交付选项

- 买家去卖家校区自取。
- 卖家可带到买家校区。
- 双方约定校车点或固定公共交付点。
- 双方另约时间，但必须选择公共区域。

#### 风险提示

跨校区交易在预约时需要提示：

- 请确认交通时间和交付地点。
- 建议高价商品当面验货后再付款。
- 不建议提前支付定金或全款。
- 如对方频繁更换地点或要求站外交易，可直接举报。

### 7.8 评价与信用

#### 首版建议

评价功能可以做成 MVP 的后半段，至少支持：

- 是否按约交付。
- 商品描述是否真实。
- 沟通是否顺畅。
- 文字评价。
- 交易完成后才能评价。

#### 信用展示

- 已认证学生
- 已完成交易数量
- 近期评价
- 被举报处理记录不直接公开，避免未经核实的标签化。

平台可以根据认证、完成交易和有效评价生成内部风险分，但不建议首版公开复杂的信用分数。

### 7.9 举报、拉黑与违规处理

#### 举报类型

- 疑似诈骗
- 商品与描述不符
- 违禁商品
- 盗图 / 侵权
- 骚扰或辱骂
- 诱导站外交易
- 虚假身份
- 其他

#### 处理能力

- 用户提交举报理由、文字说明和证据图片。
- 举报对象可以是用户、商品或聊天消息。
- 管理员查看证据和历史记录。
- 处理结果：驳回、提醒、下架、限制发布、限制沟通、封禁账号。
- 举报处理后向举报人反馈结果。

#### 运营后台最低要求

- 用户列表
- 认证审核
- 商品审核
- 举报工单
- 封禁与解封
- 审核日志
- 基础数据看板

## 8. 关键用户流程

### 8.0 微信入口新用户流程

1. 用户从微信群、朋友圈、二维码或同学分享链接进入平台。
2. 微信内打开移动端 Web App。
3. 选择或确认学校：西交利物浦大学。
4. 选择常用校区：苏州工业园区校区 / 太仓校区。
5. 使用西浦学生邮箱接收验证码或 Magic Link。
6. 完成校园邮箱认证。
7. 进入首页，默认看到本校区商品。
8. 用户可选择开启定位，用于附近推荐；也可以跳过并手动选择校区。

### 8.1 新用户购买流程

1. 通过微信链接进入平台。
2. 选择学校和常用校区。
3. 完成西浦学生邮箱认证。
4. 浏览或搜索商品。
5. 可选择开启定位，按附近、价格、分类或校区筛选。
6. 查看商品详情、卖家认证状态和交付校区。
7. 发起聊天。
8. 约定时间、地点、交易方式和是否跨校区。
9. 发起预约。
10. 当面验货并完成交付。
11. 双方确认完成并评价。

### 8.2 新用户出售流程

1. 完成校园认证。
2. 点击发布。
3. 上传图片并填写商品信息。
4. 阅读交易安全提示。
5. 选择取货校区、大致区域和是否支持跨校区。
6. 提交审核。
7. 审核通过后上架。
8. 接收买家消息。
9. 确认预约。
10. 完成交付。
11. 标记售出并评价买家。

### 8.3 风险交易处理流程

发现异常 → 用户举报 → 平台临时限制相关行为 → 管理员审核证据 → 采取处罚或恢复措施 → 通知相关用户 → 记录处理结果

### 8.4 管理员处理流程

1. 管理员登录运营管理端。
2. 查看待审核商品、举报工单和异常账号。
3. 对商品执行通过、下架、拒绝或要求修改。
4. 对用户执行提醒、禁言、限制发布、封禁或解封。
5. 查看交易争议证据，包括商品、聊天、预约和举报记录。
6. 记录处理结论并通知相关用户。
7. 在数据看板观察认证、发布、咨询、预约、成交和举报指标。

## 10. 重要业务规则

1. 一个账号只能绑定一个主要学校，首期只支持西交利物浦大学。
2. 用户需要选择常用校区，可随时手动切换浏览校区。
3. 默认展示当前校区和本校区优先商品，跨校区商品必须有明确标签。
4. 跨校区交易不是“附近交易”，需要在预约中明确交付方案。
5. 同一用户短时间内发布大量商品时触发人工审核或限流。
6. 商品售出后应自动从默认在售列表移除，但保留在卖家历史记录中。
7. 免费商品、低价数码、演出票、游戏账号等高风险类别需要更严格的风控规则。
8. 平台不承诺商品质量，不替代买卖双方完成验货。
9. 所有交易安全提示要在发布、聊天、预约和完成交易等关键节点出现，但避免频繁打扰。
10. 任何涉及校园身份、学生证、学号和交易聊天的数据，都需要最小化收集并设置访问权限。
11. 定位能力只用于附近推荐和交付点建议，不公开用户实时位置。
12. 微信 H5 链接可以作为首期入口，但正式内测仍需要云端部署、HTTPS、数据库、对象存储和邮件服务。

## 11. 数据与指标

### 11.1 核心指标

- 认证通过率
- 日 / 周活跃认证用户数
- 人均浏览商品数
- 商品发布成功率
- 商品审核通过率
- 首次消息响应率
- 预约转化率
- 交易完成率
- 商品平均售出时长
- 举报率
- 违规命中率
- 交易后满意度

### 11.2 建议的北极星指标

每月完成的真实校园交易笔数。

认证用户数很重要，但不能替代真实交易。平台最终需要验证的是“身份信任是否带来了更高的交易成功率”。

### 11.3 早期目标参考

具体数值需要结合学校规模设定。单校试点可以先观察：

- 认证用户中至少有一部分用户完成首次发布或首次咨询。
- 新发布商品在一周内获得有效咨询。
- 预约后实际完成率持续提升。
- 举报处理时效可控，严重风险事件为零。

## 14. 技术与合规注意事项

1. 学号、学生证和身份证信息属于敏感个人信息，应采用最小化采集、加密存储、权限隔离和明确的隐私告知。
2. 如果接入学校邮箱、统一身份认证或第三方实名服务，需要确认授权、接口和数据使用边界。
3. 平台需要建立用户协议、隐私政策、商品发布规则、违规处理规则和交易风险提示。
4. 涉及支付、资金托管、担保交易时，应先进行法律和支付合规评估。
5. 需要明确平台在商品质量、交易纠纷、线下人身安全和违禁品方面的责任边界。
6. 建议首个试点只选择一个学校，先通过人工审核和有限品类积累风险样本。

### 14.1 推荐技术架构与部署方式

- 用户端：手机优先的响应式 Web App / 微信内 H5，可进一步迁移为微信小程序、PWA 或原生 App。
- 管理端：独立的管理员 Web 看板，与用户端共用后端，但使用独立的管理员权限。
- 前端：Next.js + TypeScript。
- 认证与数据库：Supabase Auth + PostgreSQL。
- 商品图片与举报证据：对象存储，例如 Supabase Storage。
- 部署：Vercel、Cloudflare Pages / Workers，或后续迁移至自有云服务器。
- 邮箱认证：西浦学生邮箱 OTP 或 Magic Link；生产环境配置稳定的 SMTP 发信服务。
- 地图与定位：首期可用静态校园地图 / 示意地图 + 浏览器定位；正式版再评估腾讯地图、高德地图或学校官方地图授权。
- 微信能力：首期使用普通 H5 链接传播；若后续需要微信登录、订阅消息、模板消息、分享卡片和更稳定的微信内体验，再迁移微信小程序。

### 14.2 三种运行形态

| 运行形态 | 适合用途 | 是否适合真实运营 |
|---|---|---:|
| 本地电脑 + 本地数据库 | 个人开发、演示、设计评审、vibe coding 原型 | 否 |
| 局域网 / 临时公网地址 | 少量同学内测 | 不建议长期使用 |
| 微信 H5 前端 + 云端数据库和存储 | 西浦小范围内测 | 是 |
| 微信小程序 + 云端后端 | 稳定运营、持续增长 | 是 |

### 14.3 本地部署的限制

如果数据库、图片和后端都只在个人电脑上：

- 电脑关机、断网或 IP 变化后，平台就不可访问。
- 外部用户无法稳定访问，除非额外配置公网入口、域名和 HTTPS。
- 图片、聊天记录和认证数据可能因为硬盘故障或误操作丢失。
- 邮箱验证码、管理员权限、备份、日志和多人同时访问都需要自行维护。
- 不适合长期保存学生邮箱、聊天记录和举报证据等敏感数据。

所以，本地部署并不是“完全不能运行”，而是更适合 Demo 和封闭内测。要让真实学生持续使用，至少需要稳定的公网入口、托管数据库、文件存储、邮件发送和备份机制。

### 14.4 推荐的最小上线方案

1. 用 GitHub 管理代码。
2. 用 Next.js 同时开发学生端 H5 和管理端 Web 看板。
3. 用 Supabase 承担邮箱认证、PostgreSQL 数据库和商品图片存储。
4. 用 Vercel 或 Cloudflare 部署 Web App，绑定域名和 HTTPS。
5. 配置西浦学生邮箱 OTP / Magic Link 登录和 SMTP 发信服务。
6. 配置管理员角色、数据库行级权限、举报审核和操作日志。
7. 首期地图使用静态校园地图或轻量地图组件，避免因为地图授权和 SDK 接入拖慢验证。
8. 先用测试数据完成闭环，再邀请少量西浦同学内测。

这套方案仍然可以在本地开发和测试，但生产数据不放在个人电脑里。未来迁移到学校服务器或自有云服务器时，应保留数据库迁移脚本、环境变量配置和图片导出能力。

### 14.5 微信链接与小程序路线

#### 阶段一：微信 H5 链接

适合当前阶段。用户从微信群、朋友圈、二维码、海报进入，直接打开移动端网页。开发速度快，适合 vibe coding、产品评审和小范围内测。

限制：

- 无法完全获得小程序级别的微信系统能力。
- 消息通知、订阅提醒和分享卡片能力有限。
- 微信内浏览器兼容性需要单独测试。

#### 阶段二：微信小程序

适合完成初步验证后进入稳定运营。小程序更适合微信生态内传播，可获得更好的入口、分享、授权和消息能力。

迁移前提：

- 学生端核心流程已经稳定。
- 后端数据模型已经确定。
- 已有真实用户和交易数据证明值得继续投入。
- 已准备隐私政策、用户协议、平台规则和小程序审核所需材料。

#### 阶段三：原生 App

暂不建议作为首期目标。只有当平台已经具备持续用户规模、复杂消息能力、深度定位能力或跨学校扩展需求时，再评估独立 App。

## 15. 主要风险与解决思路

| 风险 | 影响 | 首版应对 |
|---|---|---|
| 学生不愿认证 | 无法形成用户规模 | 认证流程控制在 1 至 2 分钟，解释认证价值，优先接入学校邮箱 |
| 商品供给不足 | 用户打开后无内容 | 先做毕业季、开学季和宿舍搬迁等集中场景 |
| 学号认证被冒用 | 信任体系失效 | 优先使用学校邮箱或统一认证，不把照片上传作为唯一方式 |
| 线下交易纠纷 | 用户流失、投诉增加 | 公共区域交付、验货提示、交易状态记录、举报和证据留存 |
| 诈骗与站外导流 | 财产损失、品牌风险 | 链接识别、风险提示、异常账号限流、严重账号封禁 |
| 运营审核成本高 | 平台无法持续 | 高风险品类规则化审核，普通品类抽检 |
| 毕业后用户流失 | 用户生命周期短 | 将毕业季作为核心使用场景，并设计校友或跨校交易的后续策略 |
| 双校区体验混乱 | 用户误判距离和交付成本 | 默认本校区优先，跨校区独立标签和预约规则 |
| 定位引发隐私担忧 | 用户拒绝授权或流失 | 定位可选、可关闭，只展示大致距离和公共区域 |
| 微信 H5 能力不足 | 消息和分享体验受限 | 首期验证交易闭环，后续迁移微信小程序 |
| 本地部署不可持续 | 无法真实运营、数据风险高 | 本地只用于开发演示，内测及正式试点使用云端后端 |

## 16. 待确认问题

1. 首期是否只面向西浦学生，还是允许西浦教职工或校友浏览？
2. 西浦学生邮箱认证使用 OTP 验证码，还是 Magic Link 邮件链接？
